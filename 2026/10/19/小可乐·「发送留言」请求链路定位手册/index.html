小可乐 · 「发送留言」请求链路定位手册

发表于2026-10-19|更新于2026-10-20|安全研究
|阅读量:

适用对象：已经会用 jadx 反编译、想搞清「点一下发送，代码到底走到哪个 URL」的人
目标 APP：小可乐（包名 com.ss.android.ugc.aweme，实测版本约 40.1.0）
结论一句话：屏幕上的「发送」按钮最终走 POST /aweme/v1/comment/publish/，表单编码，正文在 text 字段。
文档性质：全部结论来自反编译源码 + 行号，不是猜测。拿不到的部分（真实字节、签名算法）在文末明确标注。

修订记录

  • v1（2026-10-19）：建立静态链路、接口字段表、查找方法、坑清单。
  • v2（2026-10-19）：补入第 12 章「LSPosed 动态验证记录」；把「屏幕按钮走 YR()」由”推断”改为”仍未证实“（运行时钩子未命中）；证据等级表同步更新。

★ 先看这段：被推翻的旧结论

原来的判断 实测结果 影响
屏幕按钮 → PublishBtnViewModel.Wb0("留言文字") ❌ 按钮走 ICommentInputManagerAbility.YR(...)；Wb0 只被键盘发送键和表情面板图标调用，参数是来源标记（"keyboard_send" / "send_icon"），不是正文 之前按这个假设做的动态验证全部无效
Wb0 是”发送入口” ⚠️ 它是 IPublishBtnAbility 接口里的一个能力方法，属于另一条入口，不是屏幕按钮那条 两条入口最终汇到同一个请求，但链路不同

本文以下内容全部以反编译源码为准。

0. 这份文档能让你拿到什么

  • 「发送」按钮到网络请求的完整 6 跳调用链（每跳给 文件:行号）
  • 最终请求的 URL、HTTP 方法、编码方式
  • 请求体的 字段表（哪些必填、哪些是埋点）
  • 三个相似接口的区分表（publish / multi_publish / publish_evaluate）
  • 可复现的查找方法：怎么反编译、怎么用 grep 从 30 万个文件里定位到这几行
  • 坑清单：反编译不全、grep 搜不到、/tmp 被清空

1. 一句话原理（先讲通整件事）

把「发一条留言」想成寄快递：

现实 代码里
你按下”寄出”按钮 onClick 触发
把手里的东西装进一个快递单（收件视频、内容、@了谁） ClickPublishParams（混淆名 C1HQW）
交给前台柜台 C1HMS.LIZJ()
柜台转给发货部门 PublishAbility.Ao1() → PublishPresenter
发货部门打包成标准包裹（表单字段） CommentPublishRequest
交给快递公司（真正上网） CommentRealApi → POST /aweme/v1/comment/publish/

每一层都只是”往下交”，真正的 URL 只在最后一层。所以找数据包的正确姿势是：从按钮往下追，一直追到 @POST 那一行。

项目 路径 / 值

为什么有两个目录：classes33.dex 之前单独反编译过、是完整的；后来做的全量反编译因为工程太大（38 万个类）在 82% 处报错退出，缺了一部分类。两个目录都要搜，这是本文最重要的实操经验。

8. 坑清单（现象 → 原因 → 修法）

现象 原因 怎么修
全量 grep 返回空，但旧目录能搜到 jadx 是分批写文件的，那个类还没写到磁盘（进度 82% 时缺后 18%） 先 find 确认文件在不在；不在就等，或换已完成的目录
ERROR - finished with errors, count: 1301 且进度停在 82% 56 个 dex / 38 万个类，巨型工程中途报错退出，不是“跑完了” 用之前单独反编译的 classes33/sources 补齐；或按单个 dex 分别反编译
反编译产物不见了 /tmp 在 macOS 重启时会被清空 产物放 ~/Desktop/android/，APK 也一起搬
以为 PublishBtnViewModel.Wb0 是按钮入口 Wb0 参数是来源标记，被键盘发送键/表情面板调用 见文首对照表；屏幕按钮的真实类尚未证实（见 12.3）
grep 6 分钟没输出 1.4G / 31 万个文件在 macOS 上较慢 先按目录或接口名收窄，别一上来全量搜
LSPosed 模块装好了但一条日志都没有 重装 APK 后模块记录是新的 enabled=0、scope 为空（旧记录随卸载一起删除） 进 LSPosed 管理器：模块 → 打开「启用模块」→ 勾选目标应用；或直接读 /data/adb/lspd/config/modules_config.db 的 modules.enabled 与 scope 表核实
模块已启用，钩子仍 0 命中，误判为”App 反 Hook” 用 Activity.onResume / TextView.setText 当探针 —— 子类会覆盖父类方法（SplashActivity、AppCompatTextView），钩父类收不到 用静态方法或 App 自己的类做探针（本次用 com.bytedance.memoryx.StringBuilderCache.get，命中即证明钩子生效）
挂上钩子后 App 卡在启动图（CPU 70%+、主线程空转） 钩了极高频方法当探针（StringBuilderCache.get 每秒上万次），Xposed 调用开销把启动拖死 探针只选”每次启动几次”的方法（如 Instrumentation.callApplicationOnCreate）；业务钩子选低频方法
设备重启后 LSPosed 报 DeadSystemException、注入失效 system_server 崩过一次，lspd 状态失效 重启手机重建环境
手机无 WiFi 时 App 卡在 SplashActivity 启动强依赖网络；无 SIM、无 WiFi 时完全不可用 USB 反向供网（gnirehtet）或接热点；重启后记得重跑并确认 VPN 授权弹窗
X.C1HQW 用 findClass("X.C1HQW", cl) 找不到 该类可能由 App 内部类加载器加载，不在 zip 顶层 ClassLoader 视野内 改成”先命中 YR，再用 param.args[3].getClass() 取真实类”再反射

11. 小词典

术语 大白话
混淆名（C1HQW） 代码被”改名”后的假名，看反编译时靠调用关系认它，别靠名字猜
@POST / @Field Retrofit 的注解：前者写”发到哪个地址”，后者写”表单里的哪个格子”
text_extra @了谁、哪个话题、在文本第几个字符——用 JSON 记下来一起发
sendMethod 你是从哪个按钮发的（界面上/键盘上/表情面板），用于埋点统计
X-Gorgon 请求头里的签名字段，防止有人伪造请求；由 native 库现算
jadx 把 APK 里的 dex 还原成 java 代码的工具

12.2 关键结论一：钩子能拦到 App 自己的调用

步骤 结果
装回模块后直接启动 App 一条 DyCtrl 日志都没有

用 StringBuilderCache.get 做探针 命中 #1 #2 #3 —— 钩子确实作用在 App 自己的代码上

结论：这台设备上 LSPosed 工作正常。此前多轮”0 命中”的主因是模块未启用 / 探针选错，不是 App 反 Hook。

12.5 本轮的设备坑（会反复遇到）

现象 处理
system_server 崩溃 → lspd 报 DeadSystemException 重启手机
冷启动卡 SplashActivity 5–15 分钟、CPU 80%+ 耐心等；实在不动就重启（重启后 1–3 分钟可用）
