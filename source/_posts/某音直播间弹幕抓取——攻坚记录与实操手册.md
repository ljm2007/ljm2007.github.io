## 0. 一句话结论

**弹幕抓到了，但是"边抓边崩"** —— 技术路线是通的（拿到 5 条真实弹幕 + 昵称 + uid），
但某音上的 Java 层 Frida 插桩会**周期性触发 Android 运行时（ART）断言崩溃**，
必须先解决稳定性问题，才能做长时间采集。

## 2. 弹幕走的是哪条路

### 2.1 为什么评论那套钩子完全没用

评论走的是 **Retrofit + HTTP**，钩 `BaseSsInterceptor.intercept` 就能拿到 URL。
但**直播间弹幕不走 HTTP**，走 **WebSocket 长连接 + protobuf 二进制** ——
套评论那套钩子上去，一条都看不到。

> 一句话：**评论是"寄快递"（一问一答），弹幕是"打电话"（长连接一直推）。**

### 2.2 链路图（实测定位到的真实类名）

```text
① 消息对象（弹幕本体）
   com.bytedance.android.livesdk.message.model.ChatMessage
   com.bytedance.android.livesdk.message.model.BaseLiveMessage   ← 所有推送消息的基类
        · getMessageMethod() → "WebcastChatMessage" / "WebcastMemberMessage" / …
          （这就是"消息类型"的来源）

② 消息分发（直播 SDK）
   com.ss.ugc.live.sdk.msg.dispatch.Dispatcher        ⚠️ 在插件的 ClassLoader 里，
   com.ss.ugc.live.sdk.msg.dispatch.IMessageDecoder       Frida 的 Java.use 可能报 not found
   com.ss.ugc.live.sdk.message.interfaces.IMessageManager
   com.ss.ugc.live.sdk.message.interfaces.OnMessageListener

③ 解码（protobuf）
   com.ss.ugc.live.sdk.platform.imbroadcast.PBDecoder

④ WebSocket 通道（字节自研 "Frontier" 框架）★
   com.bytedance.common.wschannel.server.FrontierMessageManager
   com.ss.android.ugc.aweme.frontier.ws.WSMessageManager
   com.ss.android.ugc.aweme.frontier.ws.task.WebSocketTask

⑤ 传输层（两种可能，实测都加载过）
   okhttp3.WebSocketListener.onMessage(String | ByteString)
   com.ttnet.org.chromium.net.impl.CronetBidirectionalStream.onReadCompleted(...)
```

**抓取位置的选择**：

```text
钩 ④/⑤（WS 帧）     → 覆盖率 100%，但要自己离线解 protobuf
钩 ①（消息对象）    → 直接是明文，但覆盖率取决于方法被调用的频率
```

## 3. 探针脚本踩过的坑（4 版演进）

### 3.1 第一版：在构造函数里读字段 → 全是 null

```text
ChatMessage 是 protobuf 对象，【先 new 一个空壳，再往里填值】。
所以在构造函数里读 → content = null、userInfo = null。
必须在"填完之后"的时机读（比如某个 getter 被调用时）。
```

### 3.2 第二版：读返回值时踩了 Frida 的类型坑

```js
// ❌ 错误写法
var n = String(v.getClass().getName());   // v 已经是 JS 字符串了，没有 getClass()
// ✅ 正确写法
if (typeof v === 'string') { ... }        // 先判断类型，再做别的事
```

> Frida 遇到返回 `java.lang.String` 的方法时，**直接给你 JS 字符串**，不再包一层 Java 对象。

### 3.3 第三版：钩太多 → 把某音钩崩了（见第 4 节）

当时的危险操作：

```text
· 把 ChatMessage 及其父类链上【所有返回 String 的方法】全钩了（7 个）
· 把 User 类的【29 个 getter】全钩了（User 被 UI 高频读取）
· 每个消息对象反射倒出 60 个字段（setAccessible 很贵）
· 每次调用都写日志（I/O 落在 UI 线程上）
```

### 3.4 第四版（当前版）：轻量 + 强限流 → 拿到样本，App 活着

```text
✅ 只钩 ChatMessage 链上返回 String 的方法
✅ 拿正文时才读 userInfo 的昵称/id 两个字段（不做全字段倒出）
✅ 弹幕走独立限流配额（20 条/秒）—— 不能让进场消息抢光配额
✅ 噪音消息（进场/横幅/榜单）只计数，不打日志
✅ 先原样返回值，再做记录（绝不改变原行为）
```

**一个重要的失败教训：限流要分池。**
初版用同一个"每秒 5 条"的配额，结果 `WebcastMemberMessage=68` 把配额吃光了，
真正的弹幕被丢掉 —— 看起来像"抓不到弹幕"，其实是**自己的限流把数据静默扔了**。

### 3.5 覆盖率问题（未解决）

```text
实测：WebcastChatMessage 168 次，但只有 19 次触发了那个返回正文的 getter
→ 约 11%
原因推测：那个 getter 只在【弹幕真正被显示出来】时才被调用，
        滚过屏幕没渲染的、或被合并的弹幕不会调用它。
          （标注：这是推测，未做实验确证）
```

## 4. ⚠️ 崩溃分析（本节是全篇最重要的部分）

### 4.1 现象

```text
用户视角："某音又崩了" —— App 突然消失，没有对话框，没有闪退提示。
logcat 里【搜不到】FATAL EXCEPTION / Fatal signal。
```

**⚠️ 关键：logcat 没有 ≠ 没崩。** 真正的证据在 `/data/tombstones/`。

### 4.2 证据（实测）

```text
tombstone_00   2026-10-02 10:44   uptime 24s
  pid: 15607, tid: 15908, name: #NetNormal#24
  signal 11 (SIGSEGV), code 1 (SEGV_MAPERR)
  Abort message: 'Check failed: found_virtual Didn't find oat method index
                  for virtual method: int java.io.RandomAccessFile.read(byte[])'

tombstone_01   2026-10-02 13:17   uptime 992s
  pid: 16694, tid: 17105, name: ransmitThread
  signal 11 (SIGSEGV), code 2 (SEGV_ACCERR)
  （无 Abort message）

tombstone_02   2026-10-02 14:22   uptime 316s
  pid: 9040, tid: 9145, name: TeaThread        ← 正是挂着探针的那个进程
  signal 11 (SIGSEGV), code 1 (SEGV_MAPERR), fault addr 0x1f020058000050
  Abort message: 'Check failed: existing_entry_point != nullptr
                  <<invalid-method-idx-337439936>>@0x141cea90'
  backtrace:
    #00 pc 001f020058000050  <unknown>
    #01 pc 00000000025ce4d0  /memfd:jit-cache (deleted)   ← 崩在 JIT 生成的代码里
```

### 4.3 怎么读这些证据

```text
· "Check failed: ..." = ART（安卓运行时）自己发现状态不对，主动 abort
· "existing_entry_point != nullptr" / "Didn't find oat method index"
  = 某个方法的"入口地址 / 方法索引"对不上，而且是垃圾值（337439936）
  → 这是【Java 层插桩正在被安装/拆除】时才会出现的现场
· 崩在 /memfd:jit-cache = JIT 即时编译出来的机器码里
```

### 4.4 结论与不确定度（诚实标注）

```text
【有实证的部分】
· 三次崩溃里两次是同一族的 ART 断言失败（方法索引/入口地址对不上）
· 崩之前跑的正是 Frida Java 层探针
· 某音自带 liblynxsecurity.so / libsafemode.so / 自己的 shadowhook 插桩

【确定性较高的结论】
· 这不是"JS 异常从 hook 漏出去"（那种崩溃 logcat 会有 FATAL EXCEPTION）
· 在某音上做 Java 层插桩，与它自带的插桩叠加，会周期性踩崩

【【推测，未确证】】两个加重因素
· 疑点 A：一次性钩太多高频方法（ChatMessage 全链 + User 29 个 getter）
· 疑点 B：每次"杀掉 frida 重挂新脚本"= 所有钩子同时拆桩，
          若此刻 App 正在执行被钩代码 → 直接 abort
  两个疑点都没有做过对照实验，不能断言是主因。
```

### 4.5 降险策略（按优先级）

```text
① 钩得越少越好
   只钩 1~2 个必需方法。
   ❌ 不要"把一条继承链上所有返回 String 的方法都钩一遍"
   ❌ 不要钩 User 这类被 UI 高频读取的数据类

② 不要频繁 detach
   pkill frida = 所有钩子同时拆桩。改脚本优先用 frida 的 %load（REPL 重载）。
   如果一定要重挂，尽量在 App 空闲（不在直播间、不在播放视频）时做。

③ 探针跑短跑精
   拿到样本就收，别长时间挂着。

④ 反射也要省着用
   getDeclaredFields + setAccessible + get 每对象几十次 = 很重的开销，
   只读你要的那 1~2 个字段。
```

### 4.6 排查手法（命令）

```bash
# 1) 有没有原生崩溃（真崩溃记录）
adb shell ls -lt /data/tombstones/ | head -5

# 2) 看崩溃摘要（Abort message 就在头部，第 12 行左右）
adb shell head -25 /data/tombstones/tombstone_02

# 3) logcat（注意：没搜到 FATAL 不代表没崩）
adb shell logcat -d | grep -iE "FATAL EXCEPTION|Fatal signal|SIGSEGV"

# 4) 是被杀还是自己崩（区分清楚）
adb shell logcat -d | grep -iE "lmkd|Killing [0-9]+:com.ss|Reason:"
#   "Killing ... (adj 0): remove task" = 任务被移除（从最近任务里划掉）≠ 崩溃
```

## 5. 下一步三条路线

```text
路线 A：最小钩子 + 不拆桩重挂
  只钩 2 个方法（不再钩整条链、不碰 User）
  重载脚本用 frida 的 %load，彻底不 pkill
  预期：覆盖率仍受限（约 11%），但稳定性提升

路线 B：换钩 WebSocket 帧（FrontierMessageManager）
  只钩 1 个类 → 拿全部弹幕帧，覆盖率理论上 100%
  代价：要离线解 protobuf（需要消息结构定义）

路线 C：接口直取（不钩 App）
  先探 直播间的 IM 拉取接口 是否无签名可直取
  （评论接口就是这条路：无签名、无登录、直接 200）
  代价：不一定存在这样的接口，需要先探测
```

**推荐顺序：先 C（零风险探一探）→ 再 B（一次到位）→ A 只作为兜底。**

## 6. 完整复现步骤

### 6.1 环境

```text
手机：AOSP Pixel 3 XL（Android 12，root），adb id 94NY19J44
中间：Mac（adb + frida 装在这边）
frida：17.17.0，路径 /Users/ljm2007/python312/bin/frida
adb  ：/Users/ljm2007/Library/Android/sdk/platform-tools/adb
```

> ⚠️ 非交互 SSH 下 PATH 里没有 adb 和 frida，**必须写绝对路径**。

### 6.2 确认在直播间

```bash
$ADB shell "dumpsys activity activities | grep -m1 -o 'com.ss.android.ugc.aweme/[A-Za-z.]*'"
# 期望看到：com.ss.android.ugc.aweme/.live.LivePlayActivity
```

### 6.3 挂探针

```bash
PID=$($ADB shell pidof com.ss.android.ugc.aweme | tr -d '\r')
/Users/ljm2007/python312/bin/frida -U -p $PID -l /tmp/dy_live.js -o /tmp/live.log
# 日志会写到 Mac 的 /tmp/live.log
```

### 6.4 看结果

```bash
grep "\[弹幕\]" /tmp/live.log       # 弹幕正文 + 昵称 + uid
grep "\[COUNT\]" /tmp/live.log      # 各消息类型的计数（判断探针活着）
grep "\[BOOT\]" /tmp/live.log       # 探针是否安装成功
```

### 6.5 ⚠️ 收工时

```bash
# 检查某音是否还活着
$ADB shell "pidof com.ss.android.ugc.aweme || echo APP_DEAD"
# 检查这轮有没有崩
$ADB shell "ls -lt /data/tombstones/ | head -3"
```

## 8. 术语对照（给非专业读者）

| 说法 | 大白话 |
|---|---|
| protobuf | 一种把数据压成二进制的格式，比 JSON 小，但要拿"结构说明书"才能读 |
| WebSocket | 一条一直不挂断的"电话线"，服务器可以主动往里推消息 |
| Frida / hook | 给运行中的 App "插一根探针"，看某个函数什么时候被调用、参数是什么 |
| ART | 安卓手机里负责运行 Java 代码的"发动机" |
| tombstone | 安卓把"崩溃现场"（哪个线程、哪行地址）存成的一个记录文件 |
| ClassLoader | Java 的"仓库管理员"，负责去找类；不同仓库里可能有同名类 |
