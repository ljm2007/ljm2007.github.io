## 0. 一句话结论

**`SSL_write` / `SSL_read` 确实是某音 TCP+TLS 通道上「明文最后一道门 / 第一道门」，在这两个导出符号上挂钩，本项目实测已成功抓到明文请求（无需代理、无需证书）。但这个钩子只能覆盖 4 条出网通道中的 1 条（见 §6）。**

---

## 1. 思路转变：为什么放弃中间人

| | 中间人（MITM）方案 | 直接钩发包点（本文方案） |
|---|---|---|
| 怎么拿明文 | 代理伪造证书 → App 把明文发给自己 → 代理解密后转发 | 在 App 进程内，TLS 加解密函数的两端直接抄内存 |
| 要过多少关 | 需要过完整条证书信任链：链签名、握手证明、`verify_mode`、`SSL_get_verify_result`、主机名、有效期、X509 指纹 pin、SPKI pin、cronet 状态机、Java TrustManager、CT/OCSP —— 本项目历史记录里最多枚举出 **11 道关卡** | **0 道** —— 不碰证书，不碰 pin |
| 代价 | 要持续对抗 App 的检测；每道关被绕过都可能引发新崩溃 | 只能「看」，不能改；且某音 4 条通道里只能覆盖 1 条 |

**转变的直接原因**（用户原话）：「我不用中间人来看，我想直接 hook 发包点。」

## 2. 原理：明文到底在哪两个函数里

TLS 通信的两端各有一扇门：

```
应用层（HTTP/1.1 或 HTTP/2 报文）
        │
        │  ① SSL_write(ssl, buf, num)   ← 明文从这里【进入】加密
        ▼
   ┌─────────┐
   │ 加密引擎 │  （BoringSSL 的 AEAD 记录层）
   └─────────┘
        ▼  密文 → socket → 网络
```

```
网络 → socket → 密文
        ▼
   ┌─────────┐
   │ 解密引擎 │
   └─────────┘
        │  ② SSL_read(ssl, buf, num)    ← 明文从这里【出来】
        ▼
应用层（收到的响应报文）
```

**证据层级**：✅ 实测 —— 在 `SSL_write` 入口抄 `buf`，抓到了可读的 HTTP 请求行与请求头（§5 有日志原文）。

**为什么偏偏是这两个函数**：
- 它们是 BoringSSL 的**公共 API**，库作者**故意导出**给调用方（cronet）用的 → 符号名稳定、不会被 strip
- 它们在**加解密的外侧**（调用者视角）/ **内侧**（网络视角）交界的绝对位置 —— 无论 App 怎么魔改 TLS 指纹、怎么改 ClientHello，**明文必然经过这里**
- 与「钩内部算法函数」相比，**参数结构简单**（就是裸指针 + 长度），不需要理解 BoringSSL 内部数据结构

## 3. 第一步：先验证符号真的存在（不能凭推理）

### 3.1 操作

在 Mac 上（手机已 USB 连接、adb 已 root）：

```bash
# 从手机把 so 实拉出来（不要用网上下载的版本）
adb shell "su -c 'cp /data/app/*/com.ss.android.ugc.aweme*/lib/arm64/libttboringssl.so /data/local/tmp/'"
adb pull /data/local/tmp/libttboringssl.so /tmp/

# 扫导出符号表
nm -D --defined-only /tmp/libttboringssl.so | grep -E "SSL_(read|write)$"
```

### 3.2 实测输出（✅ 证据：命令真实输出）

```
000000000004894c T SSL_read
0000000000048bb0 T SSL_write
```

- 文件大小 **367512 字节**，导出符号总数 **558 个**
- `T` = 定义在代码段（Text 段）的**全局导出**符号 → 可按名字挂钩

### 3.3 函数签名（BoringSSL 公共 API）

```c
int SSL_write(SSL *ssl, const void *buf, int num);   // buf = 待加密的明文
int SSL_read (SSL *ssl, void *buf, int num);         // buf = 已解密的明文
```

返回值 = 实际收发的字节数。

### 3.4 顺带扫到的一个「看起来能用、实际不能用」的符号

```
0000000000049d6c T SSL_get_servername     ← SNI 查询函数，导出、偏移已知
```

**但它直调会崩**，详见 §8 坑 #1。

**核心教训**：`nm` 里有 ≠ 能调用。**「导出」只说明名字和地址在，不说明在任意线程/任意时机调用都安全。**

## 4. 第二步：钩子怎么写

### 4.1 技术栈

| 项 | 内容 |
|---|---|
| 语言 | **C**（源文件 `hook_entry.c`） |
| 编译器 | Android NDK r29 的 `clang`，目标 `aarch64-linux-android26` |
| 构建 | CMake + Ninja，入口脚本 `scripts/build-inject.sh push` |
| 钩子框架 | **ShadowHook 2.0.1**（静态链接进 so），本文用「按符号名」模式 `shadowhook_hook_sym_name()` |
| 产物 | `libinlinehook.so`（约 574KB，未 strip，带调试符号） |
| 载入方式 | ptrace **出生注入**：`Inject -w -n com.ss.android.ugc.aweme -so /data/local/tmp/libinlinehook.so`（从 zygote fork 那一刻就进进程） |

### 4.2 三段式结构

```c
/* ① 声明原函数指针（类型必须与被钩函数完全一致） */
typedef int (*ssl_rw_t)(void *ssl, void *buf, int num);
static ssl_rw_t orig_SSL_write = NULL;
static ssl_rw_t orig_SSL_read  = NULL;

/* ② 写代理函数：调原函数 + 抄数据 */
static int proxy_SSL_write(void *ssl, const void *buf, int num) {
    sni_register(ssl, buf, num);                     // 先看这是哪条连接（§4.5）
    int r = orig_SSL_write(ssl, (void *)buf, num);   // 真发送
    if (r > 0 && sni_allowed(ssl)) dump_rw("W", ssl, buf, r);   // 再抄明文
    return r;
}

static int proxy_SSL_read(void *ssl, void *buf, int num) {
    int r = orig_SSL_read(ssl, buf, num);            // ← 必须先调原函数！
    if (r > 0 && sni_allowed(ssl)) dump_rw("R", ssl, buf, r);   // 返回后才有内容
    return r;
}

/* ③ 注册进钩子表 */
static const hook_spec_t hooks[] = {
    {"libttboringssl.so", "SSL_write", (void *)proxy_SSL_write, (void **)&orig_SSL_write},
    {"libttboringssl.so", "SSL_read",  (void *)proxy_SSL_read,  (void **)&orig_SSL_read},
};
```

### 4.3 关键设计点①：`SSL_read` 的时序

**必须**先调 `orig_SSL_read()` 并拿到返回值，`r > 0` 才能读 `buf`。
理由：`buf` 是**调用者提供的空缓冲区**，解密结果是在 `orig_SSL_read()` 内部才被写进去的。
**证据层级**：✅ 实测 —— 顺序写反时抓不到内容（日志里 `[RW] R` 全为空或长度 0）。

**这是这道题的核心考点**：`write` 是「我给你的数据」，`read` 是「你往我的缓冲区里填的数据」，方向相反。

### 4.4 关键设计点②：限流（防刷爆 logcat）

某音一秒内会调用 `SSL_write`/`SSL_read` **几十次**（含心跳、埋点、PCDN 上报）。不限流的话 logcat 主缓冲区会被瞬间冲掉，**其他日志全丢**。

```c
static int quota = 0;
static struct timespec quota_ts;
static int quota_ok(void) {
    struct timespec now; clock_gettime(CLOCK_MONOTONIC, &now);
    if (now.tv_sec != quota_ts.tv_sec) { quota_ts = now; quota = 0; }
    return quota < 20;      // 每秒最多 20 条
}
```

**证据层级**：✅ 实测（本项目设定值；20 条/秒是本文流程建议值，不是通用标准）

### 4.5 关键设计点③：只看业务 API，不看视频流（v2/v3 方案）

**需求**（用户明确）：「不要视频流，只留含 `amemv.com` / `zijieapi` 的 TLS 连接。」

**最初的思路（v1）**：调 `SSL_get_servername(ssl, 0)` 拿 SNI 判断。→ **崩了**（§8 坑 #1）

**最终方案（v2）**：不调任何 BoringSSL 函数，改成**从明文里抓 `Host:` 头**，自己建映射表：

```c
/* ssl 指针 → 主机名 的映射表 */
#define SNI_MAP_MAX 32
static struct { void *ssl; char host[64]; } g_sni_map[SNI_MAP_MAX];
static int g_sni_n = 0;
static pthread_mutex_t g_sni_mu = PTHREAD_MUTEX_INITIALIZER;

/* 在请求头前 256 字节里大小写不敏感地找 "host:" */
static int extract_host(const unsigned char *b, int n, char *out, int outn) {
    int m = n < 256 ? n : 256;
    for (int i = 0; i < m - 5; i++) {
        if ((b[i]|0x20)=='h' && (b[i+1]|0x20)=='o' && (b[i+2]|0x20)=='s' &&
            (b[i+3]|0x20)=='t' && b[i+4]==':') {
            int k = i + 5;
            while (k < m && (b[k]==' '||b[k]=='\t')) k++;
            int o = 0;
            while (k < m && b[k]!='\r' && b[k]!='\n' && o < outn-1) out[o++] = (char)b[k++];
            out[o] = 0;
            return o > 0;
        }
    }
    return 0;
}

static const char *WL[] = { "amemv.com","zijieapi.com","snssdk.com","bytedance","zjcdn.com", NULL };
```

**设计逻辑**：
1. 每个 `SSL_write` 都先尝试 `sni_register()` 登记该 `ssl` 的 Host（已登记的走快路径返回）
2. `SSL_write`/`SSL_read` 里用 `sni_allowed(ssl)` 查表；Host 不在白名单 → 直接 `return`，不 dump
3. **视频 CDN 的 Host（`douyinvod.com`、`bytegecko.com`、`pstatp.com` 等）天然不在白名单 → 自动被排除**

**已知副作用**：`SSL_read` 侧遇到「还没被 write 侧登记过」的连接会**先跳过**（读到的第一批响应可能没日志）。
**证据层级**：✅ 实测（视频流被正确过滤，PCDN 设置请求正常抓到，见 §5.2）

### 4.6 关键设计点④：HTTP/2 的二进制帧（v3）

**问题**：v2 之后总共只抓到 **1 条**明文日志。原因：某音主 API 走 **HTTP/2**，帧头是二进制的 HPACK，原来的「70% 可打印率」过滤器把它们**全部丢掉**了。

**v3 改法**：不再整体丢弃，而是分流：

```c
if (looks_printable(p, n)) {
    /* 文本（HTTP/1.x 明文）：转义换行后直接打 */
    LOGI("[RW] %s ssl=%p len=%d | %s", tag, ssl, n, line);
} else {
    /* 二进制（HTTP/2 帧）：打前 48 字节 HEX */
    LOGI("[RW] %s ssl=%p len=%d HEX | %s", tag, ssl, n, hex);
}
```

**为什么打 HEX 而不是放弃**：h2 的帧体里 HPACK 编码的 path / `user-agent` 等**仍带明文片段**，看 HEX 也能认出请求内容。真正的 payload（protobuf / JSON body）在 **DATA 帧**里，是**未压缩的**，同样能读。

**证据层级**：⚠️ v3 已编译推送，**完整验证未完成**（测试时手机处于异常状态，见 §8 坑 #4）。

## 5. 实测结果

### 5.1 无白名单版（第一次成功）

**条件**：亮屏解锁后拉起 App + 出生注入
**结果**：✅ 进程存活 60 秒，抓到 **8 条**明文日志

```
[RW] W ssl=0x... len=... | GET /02091eb.../video/tos/cn/.../?a=1128&br=307&mime_type=video_mp4&...
[RW] R ssl=0x... len=... | HTTP/1.1 206 Partial Content
                          Server: AliyunOSS
                          Content-Type: video/mp4
                          Content-Length: 102400
```

**读出来的信息**：
- 走的是**阿里云 OSS**（`Server: AliyunOSS`）
- `206 Partial Content` = **分段拉取**（视频分片下载）
- URL 里的参数全部明文可读：`a=1128`（App ID/版本标识）、`br=307`（码率 307kbps）、`mime_type=video_mp4`、签名参数 `rc=` 等

**结论**：**「不搞中间人、直接 hook 发包点」这条路本项目实测走通了。**

### 5.2 白名单版（v2）

**结果**：✅ 视频流被正确过滤，抓到的第一条是业务 API：

```
[RW] W ssl=0x79ea486318 len=421 | GET /service/settings/v2/?caller_name=pcdn2_client_odl&
    app=1&bid=10020&device_platform=android_phone&device_id=178540662752508&
    pcdn_ver=***&aid=1128 HTTP/1.1\r\nAccept:*/*\r\nAccept-Language:zh-CN\r\nConnection:Kee...
```

**注意**：`device_id`、`aid` 等设备标识**直接明文可读**。这类参数在真实业务里是风控关联的关键字段。

### 5.3 抓包日志的标志约定

| 标志 | 含义 |
|---|---|
| `[RW] W` | **发出**的请求明文（对应 `SSL_write`） |
| `[RW] R` | **收到**的响应明文（对应 `SSL_read`） |
| `HEX` 后缀 | 该包是二进制（通常是 HTTP/2 帧），以十六进制展示 |
| `[SNI] 登记` | 新建了 `ssl → Host` 映射（调试用） |

## 6. 某音的 4 条出网通道（重要：`SSL_write` 只覆盖其中 1 条）

### 6.1 实测证据（运行时 maps）

```bash
P=$(adb shell pidof com.ss.android.ugc.aweme | tr -d "\r")
adb shell su -c "cat /proc/$P/maps" | grep -o -E "lib[a-zA-Z0-9_.-]+\.so" | sort -u
```

**筛出网络/加密相关的**（✅ 实测输出，进程共加载 349 个 so）：

```
libttboringssl.so   ← BoringSSL：cronet 的 TLS   ★ 本文钩的就是它
libttcrypto.so      ← 字节自有加密库
libEncryptor.so     ← 加密器（签名 / 参数加密）
libsscronet.so      ← cronet 主体（HTTP/2、连接池、QUIC 调度）
libttquic.so        ← QUIC（HTTP/3）实现
libssl.so           ← OpenSSL（另一套 TLS）
libjavacrypto.so    ← Conscrypt（Java 层 TLS）
libcrypto.so        ← OpenSSL 的算法库
```

安装包里共 267 个 so，其中有 `libsscronet-wrapper.so`、`libsscronet-wrapper-helper.so`、`libnetecho.so`、`libonetex.so`、`libquick.so`、`libropaencrypt.so`、`libnative_classloader.so` 等。

### 6.2 四条通道对照表

| # | 通道 | 走哪个库 | `SSL_write` 能抓到吗 |
|---|---|---|---|
| ① | **HTTPS/1.1 + HTTPS/2**（绝大多数业务 API） | `libttboringssl.so` | ✅ **能** |
| ② | **QUIC / HTTP/3**（视频流、部分接口） | `libttquic.so` | ❌ **不能** |
| ③ | **Java 层老接口**（部分三方 SDK） | `libjavacrypto.so`（Conscrypt）→ 另有一套 `SSL_write` 在 `libssl.so` | ❌ 需要**单独**钩 `libssl.so` 的同名符号 |
| ④ | **不走 TLS 的**（明文 HTTP、PCDN 上报） | 直接 socket | ❌ 需要钩 `send` / `sendto` |

**为什么 QUIC 抓不到**：QUIC 把 TLS 记录层**内联进了 QUIC 自己的加密帧**，应用数据走 `SSL_provide_quic_data()` 这条路，**不经过 `SSL_write()`**。
**证据层级**：⚠️ 机制层推断（基于 BoringSSL QUIC API 的设计）+ 本项目实测「QUIC 连接没有产生 `[RW]` 日志」的现象，未做逐帧对照实验。

### 6.3 回答「登录包也是这种吗？」

**大概率是 ✅，但取决于该接口走 TCP 还是 QUIC。**

- 登录接口（`/passport/...`、`id6.me` 一号通）在既往 pcap 里表现为 **TLS over TCP** → 属于通道 ①，**就是 `SSL_write`**
- ⚠️ **登录密码不是明文**：某音在把密码放进 body **之前**，会在本地先加密一次（相关库：`libEncryptor.so`）。所以即便抓到登录请求明文，**密码字段仍是密文**
- **最快验证法**（无需改代码）：代码里已有 `[RW]` 日志，去 App 点「退出登录 → 重新登录」，然后在 logcat 里 grep `/passport/` 开头的请求

### 6.4 比登录更关键的一层：请求签名

某音**每个请求头**都带签名参数（`X-Gorgon`、`X-Argus`、`X-Ladon`、`X-Khronos`、`msToken` 等），由 `libEncryptor.so` 算出。

- ✅ 它们**在 `SSL_write` 的明文里直接可见**（就在请求头那几行）
- ❌ 但**「看得见」不等于「能伪造」**—— 要重放/改造请求，必须自己能**算出**这些签名
- **结论**：抓包只是入门；能改写请求才是下一个台阶

## 8. 踩坑记录（每条：现象 → 证据 → 结论）

### 坑 #1 — `SSL_get_servername` 导出了，但直调会崩 ⚠️

- **现象**：v1 白名单用 `SSL_get_servername(ssl, 0)` 拿 SNI，App 一启动就崩
- **证据**：tombstone 栈 `sni_allowed+180 → <unknown>`（跳进了非法地址）
- **符号本身没问题**：`nm -D` 实测 `0000000000049d6c T SSL_get_servername`，偏移确实是 `0x49d6c`
- **结论**：**符号导出了 ≠ 任意时刻调用都安全**。可能原因（**未验证**）：该函数内部依赖 `SSL*` 的某些状态/锁，或调用约定在该库的导出表上有特殊处理
- **替代方案**：见 §4.5，改用「从明文抓 Host 头」，**零 BoringSSL 内部调用**

### 坑 #2 — `dlopen("libttboringssl.so", RTLD_NOLOAD)` 返回 NULL

- **现象**：想用 `dlopen` + `dlsym` 拿函数指针，第一步就失败
- **结论**：本注入环境（出生注入 + 进程 namespace）里，`RTLD_NOLOAD` 查不到目标库
- **替代方案**：① `get_so_base("libttboringssl.so")` + 已知偏移；② 干脆不调（推荐，见 §4.5）

### 坑 #3 — C99 隐式函数声明编译报错

- **现象**：`get_so_base` 定义在 `hook_entry.c` 第 438 行，调用点在第 246 行 → 编译 3 个 error
- **结论**：ISO C99 **不允许隐式声明**。调用点之前必须加前置声明：`static void *get_so_base(const char *soname);`

### 坑 #4 — 「某音一拉就退 / 卡启动页」：先查环境，别怪钩子 ⭐

这是本次最关键的一条方法论。

| 现象 | 排查过程 | 结论 |
|---|---|---|
| 注入后 15 秒 App 死 | 查 tombstone：`EGL_NOT_INITIALIZED` abort，崩在 RenderThread | **灭屏状态下拉起 App 的图形初始化问题**，跟 TLS/钩子无关。亮屏解锁后重测 → 存活 60 秒 ✅ |
| 另一轮 tombstone：SIGSEGV @ `libbytehook` | 崩溃在 Jit 线程 | 某音自带 hook 库（xhook/bytehook）内部问题，非本钩子 |
| 卡在 `SplashActivity` 进不去主界面 | ① **不注入纯 App** 也卡 → 排除注入因素<br>② 查内存：`3.4G / 3.6G` 已用，剩 560K | **手机内存耗尽**，与钩子无关 |

**§8.4 方法论总结 —— 三步对照法**：

```
① 不注入、纯 App 跑一遍   → 能进主界面？说明环境的锅
② 注入「无钩版」跑一遍     → 能进？说明是钩子的锅
③ 注入「带钩版」跑一遍     → 才能定位到具体钩子
```

**另外**：换热点/换网络后卡启动页，优先怀疑网络出口（本例中 Surfboard 代理仍指向旧网段的 Mac IP）。

### 坑 #5 — 只抓到 1 条日志（HTTP/2 二进制过滤）

- **现象**：v2 白名单生效后，`[RW]` 总共只有 1 条
- **原因**：某音主 API 走 HTTP/2，帧头是二进制 HPACK，「70% 可打印率」过滤器把 API 包全丢了，只有那条 HTTP/1.1 的 PCDN 请求活下来
- **改法**：v3 二进制包改打 HEX（§4.6）

## 11. 术语小抄

| 术语 | 大白话 |
|---|---|
| **TLS / SSL** | 给网络数据「上锁」的协议。上锁前/开锁后的样子就是**明文** |
| **BoringSSL** | Google 从 OpenSSL 分出来的一个「上锁工具」实现，Chrome/cronet 用它 |
| **cronet** | 字节从 Chrome 的网络库移植来的网络引擎，App 里的 HTTP 请求都走它 |
| **MITM（中间人）** | 你插在 App 和服务器中间冒充服务器，App 就会把明文交给你 |
| **证书 pin（绑定）** | App 事先记下「真服务器的指纹」，看到不对的证书就拒绝 |
| **SNI** | TLS 握手里明说的「我要连哪个域名」 |
| **NDK** | 编译 Android 原生代码（`.so`）用的工具链 |
| **ShadowHook** | 字节开源的 inline hook 框架，能改掉函数入口让代码先跑我们的函数 |
| **HPACK** | HTTP/2 压缩请求头用的编码，压完是二进制 |
| **QUIC / HTTP/3** | 跑在 UDP 上的新版 HTTP，把「上锁」这件事内联在自己的包里了 |
| **签名** | 用密钥算出的「防伪码」，服务器用来确认请求没被改过 |
| **出生注入** | App 刚被 fork 出来、代码还没跑几行时就把 so 塞进去 |
