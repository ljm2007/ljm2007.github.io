## 0. 连接与前置（NAS → Mac）

```bash
# 连 Mac（Tailscale，NAS 上 tailscaled 提供 127.0.0.1:1055 的 SOCKS5）
sshpass -p *** ssh -o StrictHostKeyChecking=no \
  -o ProxyCommand="/opt/data/bin/socks5-nc --proxy 127.0.0.1:1055 --proxy-type socks5 %h %p" \
  ljm2007@100.103.160.49

# 查看 tailnet 里各机器是否在线
/opt/data/bin/tailscale --socket=/opt/data/tailscale/tailscaled.sock status

# 局域网兜底
sshpass -p *** ssh ljm2007@192.168.31.104
```

**坑**：
- 容器里没有 ncat，`nc` 是 busybox 版不支持 SOCKS5 → 用自带的 `/opt/data/bin/socks5-nc`
- 非交互 ssh 的 PATH 不含 `/usr/local/bin`、Android SDK、NDK → 每条命令里显式 export
- Mac 合盖会睡眠，Tailscale 上显示 `offline, last seen …`，此时任何 adb 操作都会断

## 2. 注入（出生注入）+ 四层验证

```bash
# ① 推 so（路径来自上面 find 的结果）
adb push <Mac产物路径> /data/local/tmp/libinlinehook.so
adb shell "su -c chmod 644 /data/local/tmp/libinlinehook.so"

# ② 后台起注入器（输出写进日志；这几个字符一个都不能少，少一个 adb shell 会挂住不返回）
adb shell 'exec </dev/null >/dev/null 2>&1; cd /data/local/tmp; setsid ./Inject -w -f -n <包名> -so /data/local/tmp/libinlinehook.so > /data/local/tmp/watch.log 2>&1 &'

# ③ 注入器在岗？
adb shell "pidof Inject"
adb shell "su -c 'grep TracerPid /proc/$(pidof zygote64)/status'"
```

**四层验证（从外到内，越往下越硬）**

| 层 | 命令 | 期望 |
|---|---|---|
| ① 注入器 | `adb shell "pidof Inject"` | 有 PID |
| ② 目标进程 | `adb shell "pidof <包名>"` | 有 PID |
| ③ **so 进了进程**（内核铁证） | `adb shell "su -c 'grep libinlinehook /proc/<PID>/maps'"` | `r-xp … libinlinehook.so` |
| ④ 钩子装上 | `adb shell "logcat -d --pid=<PID> \| grep HERMES_HOOK \| tail -14"` | 7 行 `hook … 安装成功` |

**包名**：正式版 `com.ss.android.ugc.aweme`；极速版 `com.ss.android.ugc.aweme.lite`（含 `aweme`，会自动下发 TLS 钩子）

**要点**：
- 日志按 `--pid=<pid>` 过滤，比 grep 包名可靠
- 前台看实时日志：去掉重定向直接跑 `./Inject -w -f …`；后台跑就 `adb shell "tail -20 /data/local/tmp/watch.log"`
- 注入器进程死了＝没人盯 zygote＝App 在裸奔（日志一条都不会有）

## 3. 看 App 崩没崩 / 为什么崩

```bash
adb shell "pidof <包名>"                                          # 空 = 挂了
adb shell "dumpsys activity activities | grep ResumedActivity"    # 前台是谁
adb shell "logcat -d | grep -E 'Fatal signal' | tail -3"
adb shell "logcat -d -t '<MM-DD HH:MM:SS>' | grep …"              # 只看某时刻之后的新记录
```

**读 tombstone**：
```
Fatal signal 5 (SIGTRAP), code 1 (TRAP_BRKPT)  ← 执行到陷阱指令 = 反篡改主动自杀
Fatal signal 5 (SIGTRAP), code -6 (SI_TKILL)   ← 被 tgkill() 主动发信号 = 程序自己的崩溃处理
```
```
#00 pc 00000000002c8db8 /data/app/…/libsscronet.so   ← so 内偏移（backtrace 里已减过基址）
```
**要点**：`so内偏移 = 运行时pc − 该 so 的加载基址`；backtrace 里的 `#00 pc` 已经是偏移，可直接用。

## 4. 符号与内存分析（都在 Mac 上跑，不在手机里）

```bash
NDK=~/Library/Android/sdk/ndk/29.0.14206865/toolchains/llvm/prebuilt/darwin-x86_64/bin

# 把 so 从手机取出来（scp 摸不到手机路径；dd 的引号会被 zsh 吃掉）
adb shell "su -c cat <手机上so的绝对路径>" > /tmp/x.so

# 符号表
$NDK/llvm-nm -D --defined-only   /tmp/x.so        # 它导出了什么
$NDK/llvm-nm -D --undefined-only /tmp/x.so        # 它要谁来提供（依赖）
$NDK/llvm-readelf -d /tmp/x.so | grep NEEDED      # 它 NEEDED 哪些库

# 剥掉符号也能看导出（BoringSSL / Conscrypt 的 SSL_* 都还在）
$NDK/llvm-nm -D --defined-only /tmp/x.so | grep -E "SSL_|X509"

# 地址 → 函数名（stripped 的 so 返回 ?? ??:0，属正常）
$NDK/llvm-addr2line -e /tmp/x.so -f -C 0x2c8db8
```

**今天靠这几个命令得出的关键事实**：
- `libsscronet.so` 的 NEEDED 里有 `libttboringssl.so` / `libttcrypto.so`，它的 SSL 符号全是 `U`（导入）→ **cronet 没有内嵌第二套 BoringSSL**
- `/proc/<pid>/maps` 里出现 `/apex/com.android.conscrypt/lib64/libssl.so` → 系统 Java 层 TLS 栈（Conscrypt），这才是“另一套 SSL”
- 极速版与正式版的网络库结构一致（ttboringssl / ttcrypto / sscronet 都在）

## 5. 网络与 iptables（抓包必备，也是今天最大的自伤来源）

```bash
# 封 QUIC（抖音优先走 UDP 443，不封抓不到包）
adb shell "su -c 'iptables -A OUTPUT -p udp --dport 443 -j DROP'"

# 查看（IPv4 / IPv6 必须分开查！）
adb shell "su -c 'iptables  -S OUTPUT | grep 443'"
adb shell "su -c 'ip6tables -S OUTPUT | grep 443'"

# 删除多余规则
adb shell "su -c 'iptables -D OUTPUT -p udp --dport 443 -j DROP'"

# 挂代理 / 清代理（Mac IP 现查）
adb shell "settings put global http_proxy $(ipconfig getifaddr en0):8080"
adb shell "settings put global http_proxy :0"
adb shell "settings get global http_proxy"
```

**今天的踩坑**：
1. 把 `iptables` 和 `ip6tables` 两条命令的输出混在一起读，误判“IPv4 里有 tcp 443 DROP” → **查两张表必须分两次看**
2. 往 IPv6 OUTPUT 加了 `-p tcp --dport 443 -j DROP` 想修连通性，结果**抖音所有 IPv6 TLS 出口被掐断**，触发它自己的崩溃处理（`SI_TKILL`）→ 环境脏了之后所有实验结论都不可信
3. 正确状态：**IPv4 只留一条 `-p udp --dport 443 -j DROP`**，IPv6 一条都不留

**排错顺序**：先怀疑环境（规则/代理/残进程），再怀疑代码。

## 7. 今天排查的方法论（比命令值钱）

| 手法 | 今天怎么用的 |
|---|---|
| **二分法** | 怀疑 4 颗 conscrypt 钩 → 先删最可疑的那颗 → 还崩 → 再删剩下 3 颗 → **结论：不是 conscrypt** |
| **控制实验** | 不注入（`pm clear` 后干净数据）→ 活；注入 → 崩 → 证明“钩子/注入动作”才是变量 |
| **拿干净环境做基准** | 脏环境（残留 iptables）下的所有崩溃结论都不可信，先把环境洗回标准状态 |
| **对齐时间再看内容** | 日志里全是历史记录，只认目标时间点之后的：`logcat -d -t '<时间>'` |
| **关键词出现 ≠ 问题发生** | `pm clear` 后健康运行也有 `safemode_storage` 行，它只是例行访问日志 |
| **铁证优先** | 日志可能被过滤/误读，`/proc/<pid>/maps` 是内核事实 |

**今天的结论（截至 12:50）**
- 正式版：装 7 颗 ttboringssl 钩 → 9 秒后 `SIGTRAP/TRAP_BRKPT`，崩在 `libsscronet.so`（疑似反篡改/完整性校验），**未解决**
- 极速版：同样 7 颗钩 → 注入成功、钩子持续工作、App 稳定不崩 → **极速版是当前可用的突破口**
- 待验证：极速版抓包是否出明文（第 6 节）
- 待查：`libsscronet.so +0x2c8db8` 到底是什么（stripped，下一步用 IDA 静态看）
