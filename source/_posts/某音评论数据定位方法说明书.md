> 本文重点不是记住某个类名，而是学会一套**从界面反推数据来源，再定位网络接口和接收链路**的方法。
>
> 目标 APK：`com.ss.android.ugc.aweme`

>

## 第 0 章　先用一个比喻理解整条路线

把评论显示过程想象成餐馆上菜：

```text
后厨做菜       = 网络接口拿到评论数据
传菜员端上菜   = Presenter / ViewModel 传递数据
服务员摆盘     = Adapter / ViewHolder 绑定控件
客人看到菜     = uiautomator 控件树
```

我们已经能看到“桌上的菜”，但不能只盯着菜名猜后厨在哪里。正确做法是沿着传菜路线反向追：

```text
界面控件
  ↓
控件所属组件
  ↓
Adapter / ViewHolder
  ↓
CommentItemList
  ↓
CommentFetchPresenter / Fetcher
  ↓
CommentListApi
  ↓
真实 URL
  ↓
HTTP/2 或 QUIC
  ↓
SSL_read / QUIC 接收与解码
```

**核心原则：控件树负责告诉我们“数据已经到了哪里”，APK 静态分析负责告诉我们“数据从哪里来”。**

## 第 1 章　本次最终找到的结果

### 1.1 普通视频评论列表接口

APK 源码中的 Retrofit 接口明确写着：

```java
@GET("https://aweme.snssdk.com/aweme/v2/comment/list/")
Observable<CommentItemList> loadMoreComments(...)
```

因此，普通视频评论列表接口是：

```text
https://aweme.snssdk.com/aweme/v2/comment/list/
```

这是**源码实证**，不是根据字符串猜测。

### 1.2 返回数据类型

接口返回：

```java
Observable<CommentItemList>
```

可以理解成：

```text
网络请求完成后，会得到一个 CommentItemList 评论列表对象
```

### 1.3 主要请求参数

接口中已经确认的参数包括：

| 参数 | 大白话含义 |
|---|---|
| `aweme_id` | 当前视频的 ID |
| `cursor` | 评论翻页游标 |
| `count` | 本次要取多少条 |
| `insert_ids` | 需要插入或置顶的评论 ID |
| `channel_id` | 渠道或场景编号 |
| `city` | 城市信息 |
| `page_source` | 从哪个页面进入 |
| `aweme_author` | 视频作者信息 |
| `item_type` | 视频类型 |
| `comment_aggregation` | 评论聚合相关参数 |
| `top_query_word` | 评论区顶部搜索词 |
| `is_preload` | 是否是预加载 |
| `favorite_comment_timestamp` | 重点/收藏评论时间信息 |
| `group_id` | 视频所属分组 ID |
| `service_id` | 服务类型 |
| `comment_scene` | 评论场景 |
| `is_24_story` | 是否为 24 小时动态类内容 |
| `aweme_type` | 视频类型 |

其中最关键的是：

```text
aweme_id + cursor + count + is_preload
```

这四个字段基本对应：

```text
给哪个视频取评论
从第几页开始
取多少条
是不是提前加载
```

### 1.4 评论操作接口

同一个 `CommentListApi` 中还发现了其他接口：

```text
POST /aweme/v1/comment/delete/
GET  /aweme/v2/shop/promotion/comments/
GET  /aweme/v2/shop/promotion/comment/action/
```

它们分别更像：

| 接口 | 用途判断 |
|---|---|
| `/aweme/v1/comment/delete/` | 删除评论 |
| `/aweme/v2/shop/promotion/comments/` | 商品/团购评论 |
| `/aweme/v2/shop/promotion/comment/action/` | 商品评论操作 |

本文追踪的目标是普通视频评论，因此重点接口仍然是：

```text
/aweme/v2/comment/list/
```

## 第 2 章　第一步：先从控件树开始

### 2.1 为什么先看控件树

如果直接从几百 MB 的 APK 里搜索，结果会非常多。先看界面，可以获得一批“已知答案”：

```text
用户名
评论正文
发布时间
IP 属地
点赞数
回复按钮
```

这些文字相当于“路标”。以后看到某个类或字段时，可以判断它是否真的对应评论显示。

### 2.2 控件树中能看到什么

之前评论区控件树中出现过类似内容：

```text
content-desc="悦欣,图一二 跟评，欣欣天天开心,8小时前, · 广西,回复 按钮,"
content-desc="指尖温柔,你不主动怎么有故事[比心],45分钟前, · 湖南,回复 按钮,"
content-desc="赞1,未选中"
content-desc="踩,未选中"
```

这说明控件层已经拿到了：

```text
用户名 + 正文 + 时间 + 属地 + 操作状态
```

### 2.3 控件树的局限

控件树中的：

```xml
class="android.widget.TextView"
```

只说明最后显示文字的控件类型，不等于真正的数据类。

它不能单独告诉我们：

- 哪个网络类获取了评论；
- 哪个类解析了响应；
- 评论是否来自缓存；
- 评论是否通过 JSON、Protobuf 或其他格式传输。

所以控件树是**终点证据**，不是完整调用链。

| 界面内容 | 可能的字段 |

本次 APK 字符串扫描确实找到了：

```text

```

因此，这些字段线索得到了 APK 字符串层面的支持。

## 第 4 章　第三步：从 APK 中找评论业务组件

### 4.1 不要只搜“评论”两个字

大 APK 里“comment”可能出现几千次。更有效的搜索组合是：

```text
CommentFetchPresenter
CommentListPageFragment
CommentListState
CommentEmbedLoadMore
CommentListMergeParam
CommentItemList
CommentListApi
loadMoreComments
```

搜索目标不是一个关键词，而是一条业务链。

### 4.2 本次找到的关键组件

| 组件 | 作用判断 | 证据级别 |
|---|---|---|
| `CommentFetchPresenter` | 评论获取成功/失败回调 | 字符串中出现 `onSuccess`，较强线索 |
| `CommentListPageFragment` | 评论页面容器 | 类名与页面职责直接对应 |
| `CommentListState` | 评论列表状态 | 类名与状态字段对应 |
| `CommentEmbedLoadMore` | 评论区加载更多 | 字符串出现 `fetch err` |
| `CommentListMergeParam` | 合并评论或预加载结果 | 类名与合并参数对应 |
| `CommentItemList` | 评论列表响应对象 | Retrofit 返回类型，强证据 |
| `CommentListApi` | Retrofit 网络接口 | 源码接口定义，强证据 |

### 4.3 关键 Fetcher：`X.C1H2V`

反编译出的 `X.C1H2V` 中有：

```java
AbstractFetcher<
    C2351601H2j,
    CommentItemList,
    C2351601H2j,
    CommentItemList
>
```

这说明：

```text
输入：C2351601H2j 评论请求参数
输出：CommentItemList 评论列表
```

它里面还调用了：

```java
CommentListApi commentListApi = C2376561I0j.LIZIZ;
commentListApi.loadMoreComments(...);
```

并且返回：

```java
Observable<CommentItemList>
```

这已经把“评论页面”和“网络接口”连起来了。

## 第 5 章　第四步：确认 Retrofit 的真实接口

### 5.1 API 对象在哪里创建

源码 `X.C2376561I0j` 中确认：

```java
CommentListApi LIZIZ =
    RetrofitFactory.LIZIZ(false)
        .createBuilder("https://aweme.snssdk.com")
        .build()
        .create(CommentListApi.class);
```

大白话：

```text
先选 aweme.snssdk.com 作为服务器
再根据 CommentListApi 接口自动生成网络请求对象
```

### 5.2 接口定义

源码中实际存在：

```java
public interface CommentListApi {
    @GET("https://aweme.snssdk.com/aweme/v2/comment/list/")
    Observable<CommentItemList> loadMoreComments(...);
}
```

这一条是本文最重要的静态证据。

## 第 6 章　第五步：确认评论是否预加载

之前只在“点击评论按钮”时抓包，可能看不到请求。源码和字符串给出了原因线索：

```text
CommentListPageFragment preload
comment_preload_real_time
comment_preload_opt_ab_v2
comment_preload_limit_fix_setting
```

接口参数中还明确有：

```text
is_preload
```

因此更合理的流程是：

```text
视频刚滑到屏幕
  ↓
评论列表预加载
  ↓
CommentListApi.loadMoreComments()
  ↓
CommentItemList
  ↓
打开评论面板时直接显示
```

这解释了之前的现象：

```text
点评论按钮后，Hook 没看到新的 comment 请求
```

这不等于“没有评论请求”，也可能是请求已经在点按钮之前完成。

### 证据等级说明

- `is_preload` 出现在真实接口参数中：**实测静态证据**；
- `CommentListPageFragment preload` 出现在 APK 字符串中：**字符串证据**；
- 本次具体视频一定是在滑动时预加载：**尚未用请求时间戳直接验证**。

所以本文写作时应说“很可能/有证据支持预加载”，不写成“所有视频都一定预加载”。

## 第 7 章　完整调用链

目前可以把调用链写成：

```text
界面上的评论控件
    ↓
评论列表 Adapter / ViewHolder
    ↓
CommentItemList
    ↓
CommentViewModel / CommentListState
    ↓
X.C1H2V
    ↓
C2376561I0j.LIZIZ
    ↓
CommentListApi.loadMoreComments()
    ↓
GET https://aweme.snssdk.com/aweme/v2/comment/list/
    ↓
Retrofit / TTNet / Cronet 网络层
    ↓
HTTP/2 或 HTTP/3 解帧
    ↓
响应体解码
    ↓
CommentItemList
```

这里有两条方向：

### 从界面向上追

```text
TextView / content-desc
  ↓
ViewHolder
  ↓
Adapter
  ↓
CommentItemList
```

### 从网络向下追

```text
CommentListApi
  ↓
Retrofit 请求
  ↓
TTNet / Cronet
  ↓
SSL 或 QUIC
  ↓
CommentItemList
```

两条路线在 `CommentItemList` 汇合。

## 第 8 章　如何把 Java 层继续连到接收封包位置

### 情况 A：普通 TCP + TLS

如果请求走普通 HTTPS，链路可能是：

```text
SSL_read()
  ↓
HTTP/2 解帧
  ↓
Retrofit 响应转换器
  ↓
CommentItemList
```

此时可以观察：

```text
libssl.so
libttboringssl.so
SSL_read
```

但 HTTP/2 可能是二进制帧，`SSL_read` 日志里不一定出现完整 URL 或中文评论。

### 情况 B：QUIC / HTTP3

如果请求走 QUIC，链路可能是：

```text
UDP 接收
  ↓
libttquic.so / libsscronet.so
  ↓
QUIC 解密
  ↓
HTTP/3 解帧
  ↓
CommentListApi
```

这时普通 `SSL_read` 可能看不到评论请求。

### 情况 C：本地缓存或预取

如果控件显示评论，但点击评论按钮时没有网络流量，可能是：

```text
之前已经请求过
  ↓
评论数据保存在内存或缓存
  ↓
打开面板时直接绑定控件
```

因此必须把“滑到视频的时间”和“评论面板打开的时间”分开观察。

## 第 9 章　实战验证方法

### 9.1 先记录界面标记

从控件树记录：

```text
评论数量
用户名
评论正文前几个字
时间
属地
```

例如：

```text
评论 29
冷天,也是看到日出了
千夜瑭月,东方欲晓
```

这些是“已知明文标记”。

### 9.2 再做动作

本文流程建议的动作顺序：

```text
1. 记录当前时间
2. 滑到一个新视频
3. 等待视频和评论数量出现
4. 立刻记录 Hook 日志
5. 打开评论区
6. 再记录一次控件树
7. 比较请求时间和评论出现时间
```

不要只在点击评论按钮后才开始抓，因为请求可能更早发生。

### 9.3 Hook 日志的判断

| 现象 | 更合理的解释 |
|---|---|
| 出现 `/aweme/v2/comment/list/` | 已直接定位评论列表请求 |
| 只有 `aweme.snssdk.com`，没有路径 | 可能是 HTTP/2 二进制或日志截断 |
| `SSL_read` 有调用，评论文字搜不到 | 可能是压缩、Protobuf 或 HTTP/2 帧 |
| 评论控件变化，但 SSL 日志不变 | 可能来自缓存、预取、QUIC 或另一网络库 |
| 只有视频 CDN 的 `206 Partial Content` | 当前窗口主要是视频流，不是评论接口 |
| 点击评论后没有新请求，但评论立即显示 | 更像提前加载或缓存 |

## 第 10 章　这次没有确认的部分

以下内容目前不能写成确定结论：

1. `CommentItemList` 的全部字段名尚未完整还原；
2. 本次实际展示的评论是否来自 `/aweme/v2/comment/list/`，还没有用时间戳直接对账；
3. 评论请求具体走 TCP/TLS 还是 QUIC/HTTP3，尚未完成协议层确认；
4. APK 字符串中的其他路径不一定属于当前视频评论流程；
5. `CommentFetchPresenter` 的完整包名和具体 `onSuccess` 实现还需要继续从反编译源码中定位；
6. 某些评论可能来自缓存、预加载或 Feed 一起返回，而不是打开面板时单独请求。

这些是“待验证”，不是“已经证明”。
